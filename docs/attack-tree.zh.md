# 攻击树：RPMB 密钥可能来自哪里？

一份按测试成本排序的分析计划，每个节点一行诚实的状态。它同时也是贡献者可以直接开工的清单：
每个未定论的节点都写明能一次性决定它的那个最便宜的实验。

测量与数据：2026 年 10–11 月。我们自己的测量标为 **[我们]**，无法复现的第三方说法标为
**[3rd]**，仅认为合理但未验证的标为 **[待定]**。

范围重申：自己的硬件、设备维修、不涉及 DRM 规避；本仓库不含任何密钥材料或序列号。
见 [LEGAL.zh.md](../LEGAL.zh.md)。

---

## 0. 诚实地说明目标

我们要**修主板**，而 RPMB 密钥只关系到一个子目标：对 RPMB 分区做认证写入。
这些主板上其余一切都不需要它 —— 见 [sony-partitions.zh.md](sony-partitions.zh.md)。

因此这棵树有两个根，而且它们不是同一个问题：

| 根 | 问题 | 状态 |
|---|---|---|
| **R1** | 我们能否取得某张卡的 RPMB 密钥？ | 一张卡可以 **[3rd 已证实]**，我们的两张 16 GB 卡不行 |
| **R2** | 维修需不需要它？ | 对我们迄今测量过的每一步都 **不需要** |

关于 R1 已有一个正面数据点：一张卡的密钥通过商用治具取得，并经密码学验证
（派生的 MAC 相符）。该结果成立，但它不是来自 T48，我们用现有硬件无法复现那条路径。

## 1. 树

```
R1  取得某张卡的 RPMB 密钥
│
├── A  卡内嵌的启动识别元数据                    [3rd] + [我们：阴性]
│      说法：0x20000000 处的元数据区，80 页，含 CID、
│      写计数器与 32 字节密钥。工具日志："RPMB key is VALID"。
│      我们的测试：两张 16 GB 卡从头到尾全搜 —— 没有元数据块、
│      任何字节序下都没有 CID、没有 "Boot Identification"。
│      结论：这条路在某些三星 die 上存在，在我们的卡上不存在。
│      第二个大得多的阴性结果：我们手边已有的 694 份 EasyJTAG 日志
│      （11 MB，v1.6.4–2.0.2）中，identification 出现在 0 行、
│      密钥出现在 0 行 —— 见 ufpi-findings.zh.md。
│
├── B  经由厂商命令接口进入控制器 RAM            [待定]  ← 目前唯一活着的分支
│      BootROM 敲门（CMD1 0x69FF87A9）、CMD60/CMD62 解锁、
│      读 RAM 后门（CMD62 0x10210002），随后 CMD35/36/38/17。
│      oranav 已就 VTU00M 文档化（GPLv3，只链接不复制）。
│      这一能力确实存在于某处：EasyJTAG 导出
│      eMMC_SamsungBootTrickCMDInit/Finish——具名的两阶段厂商技巧。
│      我们的障碍：无法判断 T48 位流到底是否把 CMD60/CMD62
│      转发给卡 —— 编程器在这一层不暴露卡片应答。
│      → 这就是 issue #1 与逻辑分析仪测量系列。
│
├── C  直接从 RPMB 分区读出                      [我们：已关闭]
│      对 RPMB 区域的裸读返回 Result 0x0001（通用失败）；
│      读到 16384 字节，99.8% 为零，唯一的非零字节就是 Result 字段。
│      已在实物上证明两次。关闭。
│
├── D  从主机软件或镜像中恢复                    [我们：已关闭]
│      完整用户区备份离线分析：联发科 DRM 库中有符号

│      从不存于镜像。对含 DRM 字符串区域做熵检测：
│      任何位置都没有 32 字节的随机块。关闭。
│
├── E  暴力破解 / 穷举搜索                       [我们：已关闭]
│      用一个已知正确的帧测试了 25,165,728 个候选密钥：
│      零命中。256 位密钥上的 HMAC-SHA-256 不可搜索。关闭。
│
├── F  绕过校验而非取得密钥（EMFI）              [3rd]  对我们而言超出范围
│      已发表的成果：无密钥写入（可读可写）。需要 glitch 线圈与
│      脉冲发生器。本项目不动烙铁，而且它也产不出密钥。不是我们的路。
│
└── G  询问拥有该设备的人                        [待定]  ← 最便宜的分支

       对我们零成本，而且一个答案比我们一周的工作更有决定性。

维修那条根，与之并行：

```
R2  维修主板
│
├── H  不涉及 RPMB 的启动链                      [我们：待定]
│      已验证：写入与擦除路径逐字节一致，extCSD 可读，
│      分区访问可切换。迄今测量过的每一步都不需要密钥。

├── I  全新卡的密钥预置                          [待定]
│      当计数器为 0 时，电视机会自己写入密钥吗？在 T48 上

│

│      报告的机制：重写 CSD —— 清除 CSD 第 14 字节的 bit 12/13，
│      重算 CRC7，CMD16 16 → CMD27，前面还需固件解锁操作码，
│      而我们的 T48 不实现这些操作码。独立子树，且有破坏性：
│      必须先做完整备份。
│
└── K  卡本身的固件更新（FFU）                   [我们：已测量，取决于 B]

       任何编程器能否走到那一步。

       读取控制器固件。T48 没有这一步——障碍全在这里，不在卡。

## 2. 各节点详情，按"决定性实验有多便宜"排序

### B —— 控制器 RAM（在我们的卡上，这是唯一仍通向密钥的分支）

整个分支系于一个二元事实：**一个子操作码为 `0x7E` 的 `0x27` 数据包，
到底有没有在 eMMC 总线上产生波形？**

最省钱的判法：在 BGA 座子适配器上把逻辑分析仪接到 CLK/CMD/DAT0，四通道即可，
24 MS/s 就够，因为我们只需要"有无边沿"。先发 `0x46`（一个已知确实生效的命令）
作为阳性对照，再在同一会话、同一张卡上发 `0x7E`。

结果对应关系：

| 结果 | 含义 |
|---|---|
| `0x46` 有总线活动，`0x7E` 没有 | 位流不转发厂商命令 → 分支 B 在 T48 上死路，路线 3（自制位流）成为强制项 |
| `0x7E` 有总线活动 | 转发生效 → 未决问题转移到卡片应答（我们仍看不到）；下一步是解码 DAT0 上的响应 |
| 两者都无活动 | 我们对命令闸门的模型有误 → 从总线重新推导 |

**不要**用扫子操作码的方式试探。`0xFF` 会把编程器卡死直到物理重插，而映射
`sub_op = 0x40 + CMD` 恰好把 CMD0、CMD15、CMD24（写）与 CMD28/29（写保护）
放进一个扫描会穿过的区间。

### G —— 关于工具的问题

对我们零成本，期望价值最高。具体请求见 README 第 4 节与 issue #3/#4。
我们需要 UFPI/EasyJTAG 持有者提供的，按优先级：

1. 工具是否肯发送 `CMD62 0xEFAC62EC`，随后 `CMD62 0x10210002`，卡片答了什么。
   "工具拒绝执行"也是有用的答案。
2. RPMB 界面里显示的密钥来自哪里 —— 元数据块还是控制器 —— 外加确切菜单路径。
3. 该功能的一次 USB 抓包，按编程器 VID/PID 过滤。

### A —— 元数据之说

由第三方日志支撑而保持开放，但对我们这两张卡已被直接搜索否证。能改变结论的东西：
一张在工具上显示密钥的卡的转储，加上它读取时用的字节偏移。这样我们就能检查
该偏移在 T48 上是否可寻址。

### C、D、E —— 已关闭的分支

由测量关闭，列在此处是为了避免有人再把精力投在重启这些分支上。除非台面上
新增别的卡型号，它们保持关闭：这些结论是 die 特定的。

### I —— 预置问题

整棵树里最便宜的实验，也是对维修影响最大的一项：准备 U 盘（FAT32，`.pkg` 放根目录），
用一张计数器为 0 的卡让电视从 U 盘启动，记录 LED 状态并观察是否出现 RPMB 写入。
如果电视机会自己给卡预置密钥，密钥问题对维修就彻底不再重要。

### K —— 固件更新这个问题

障碍不在卡。就我们台面上的 587 份 extCSD 转储统计，531 份报告
`FFU_FEATURE_SUPPORT`（`EXT_CSD[308] = 1`），我们这一型号 AJTD4R 的九份转储全部如此，
FW_REV 02.00。对这个 die 而言，固件更新是一项真实存在的功能。

但仍有两件事阻止我们去执行一次，两者都关于"可逆性"：

| 障碍 | 原因 |
|---|---|
| 传输路径 | 文档化的流程以 `CMD60 / 0xEFAC60FC` 开头；任何编程器能否把它送上总线，正是节点 B |
| 无法回退 | 在 T48 上没有备份控制器固件的路径 —— 要导出它，仍需那条尚未证实的读 RAM 后门。镜像放错不会"安全地失败"：它替换的是控制器启动执行的那段代码。 |

镜像这一侧部分有解：厂商固件库并非按容量区分，我们两张卡里有一张存在完全对应的镜像
（同 PNM、同控制器家族），另一张在这个容量上没有 —— 最接近的是 32 GB 的姊妹型号文件。
即便如此，动手前仍应先对照 `EXT_CSD[254..255]` 校验匹配。

所以对"我们能不能在自己的卡上试一次 FFU"的诚实回答是：**还不行，而且不能在有真实镜像的
那张卡上。** 这是本项目里唯一无法撤销的操作，它的判定条件仍未回答，而节点 B 的答案只需要
一个下午的逻辑分析仪。如果那答案是肯定的，第一次 FFU 也应落在空白的样板卡上 ——
并且始终是一项明确的决定，不是试验。

## 3. 我们自己就能做的事，按成本排序

以下任何一项都不需要新硬件。按每小时价值排序。

1. **位流差分 —— 已做，结果为负。** `.alg` 收集在本地是完整的：354 个容器，
   五个 eMMC 家族，每个都有 `_18` 与 `_33` 两个变体。我们按原计划对解压后的流做了 XOR
   （每个 340 604 字节 = 170 302 个 16 位字），结果并未达到预期。本应只在 IO 标准上
   不同的那一对（`GEN_18`/`GEN_33`）有 9.19% 的字节不同；跨家族 XOR
   （`EMMC_41_18` 对 `NAND_15`）有 10.80% —— **没有对比度**，而且差异均匀分布在所有位位置
   与整个流上。原因：每个变体都是独立布局并走线的设计，不是参数化的派生版本，
   因此两个已走线的 Spartan-6 流相减显示的是走线，不是 IO 属性。
   **引脚分配无法由此推出。** 这条路剩下的选项：直接解码配置帧地址，或者回到电路板本身。
   数据与完整表格见 [../WEITERE-WEGE.md](../WEITERE-WEGE.md)。
2. **更新版 Xgpro 的静态差分。** 我们手上有两个安装包版本。对两者做字符串
   与导入表差分，可以看出厂商命令面是否扩大 —— 完全不碰硬件。
   与位流差分同一方法：比较，而不是猜。
3. **UFPI 操作码路径 —— 已有结论，没有剩余测试。** 我们对已解包 UFPI 二进制自身的静态
   分析显示：两个 RPMB worker 各 0x89 字节，且都不含读取动作。`0x93` worker 从主机输入的
   32 字节密钥取自一个输入框（`"Enter RPMB Auth Key (32 bytes)"`，校验为 64 个十六进制
   字符），把 `req[0..3] = 0x93` 加这 32 字节交给编程器 —— 36 字节，3 秒超时；`0x94`
   结构相同，用于认证。UFPI 同样没有主机侧 RPMB 帧构造器，也没有读密钥路径。
   这恰恰是 issue #4 的论据：EasyJTAG 日志显示的密钥来自一次元数据读取。所以未决问题
   不是"0x93 读什么"，而是"EasyJTAG 固件里是哪段代码在做那次元数据读取"。
4. **自家镜像里的两项离线检查。** (a) `MTDRM_RPMBLoadMacKey` 证明主机侧是通过
   RPMB 读取密钥的；沿引导加载器的调用链走下去，可以看出它期望*哪些* RPMB 帧。
   (b) 在我们已有的分区表里搜索 EasyJTAG 日志暴露出的那些名字：`rpmbak`、
   `keystorage`、`keyrefuge`、`keydata`、`keystore`、`keymaster`。名为 **rpmbak**
   的分区就是存放在用户区的 RPMB 备份——如果我们的主板上有这样的分区，那么就
   存在一条完全不需要密钥的恢复路径。两项都是对我们自己备份的离线分析，无风险。
5. **模拟 RPMB 帧层。** 用合成的密钥/nonce/计数器算 MAC，并对照 JEDEC 布局
   校验我们的字段打包规则，使这段代码在接触真实卡片之前已被证明。
6. **电视上的 U 盘测试**（节点 I）。不动烙铁、可逆，而且它回答的是一个
   编程器根本无法回答的问题。

之后有了逻辑分析仪：节点 B，外加录制一次 `.alg` 上传期间 FPGA 的行为
（路线 3，第 4 步）。

## 4. 我们刻意不做的尝试

- 不焊接、不在 die 上放探针、不用 glitch 线圈（项目规则；节点 F 本就是他人的工作）。
- 不用破坏性命令当探针：读 RAM 后门未打开时，`CMD38` 是擦除。
- 不做子操作码扫描；不做没有完整备份的写入；本仓库任何文件都不含密钥材料或序列号。
- 不转载厂商固件字节；第三方代码一律链接而非复制。
