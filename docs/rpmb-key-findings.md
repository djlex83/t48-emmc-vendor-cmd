# RPMB key — what two videos and the OP-TEE issue establish

**Status: third-party claims, not our own measurements.** Every statement below comes from
tutorial videos or a public issue tracker, not from hardware we ran. It is published
because it shapes our search strategy, not because it is verified.

---

## Video 1 — UFI eMMC ToolBox, Samsung moviNAND

* The RPMB key **sits in the controller firmware dump**. `Read eMMC Fw` reads it out; the
  displayed value is then entered as the key in `Enter RPMB Key`. For Samsung this is the
  route to the plaintext key — it has nothing to do with the user area.
* `Read eMMC Fw` is **read-only** — no backup obligation, no write risk.
* The **counter cannot be set directly.** It only comes back through an RPMB frame write
  against the old RPMB partition.
* The counter is **not boot-critical**: the video boots with counter 0. What is lost is the
  old encrypted data, not the device.
* The original IC stays untouched; experiments run on a second card. That is exactly the
  rule that applies to us.

## Video 2 — a second box, phone repair

* The box has a `Read RPMB Key` that reads the key **directly from the intact card**
  (Samsung). Then `Write RPMB Key` onto a blank card → status
  `Legacy write protection mode`, counter 0.
* After that the card still reports `Device not boot inbuilt` /
  `Partition configuration 0` / `User area invalid for boot`. That is a boot blocker
  **independent of the key** and lives purely in the extCSD partition configuration. Only
  after that fix does it reach EDL mode and continue flashing.
* Consequence: the key alone is not enough — `PARTITION_CONFIG` must match the device, or
  even a correctly provisioned card will not boot.

## OP-TEE issue #4019

* The key is **unique per eMMC** and generated by the TEE (`CFG_RPMB_WRITE_KEY=y` is a
  factory build that writes it into the card once). Afterwards `tee_rpmb_init()` detects
  that it is already programmed.
* The key is **neither read back nor re-derived**; the issue names neither fuses nor OTP
  nor HUK nor controller firmware as a source.
* The only exposure described: the normal world could induce the secure world to
  overwrite it — then the key would cross the bus in plaintext.
* "once you have the RPMB key the security of RPMB is gone."

## What this means for our negative result

Our own attempts found nothing: the key is neither in the user dump nor derivable from
CID/CSD — **25,165,728 HMAC checks without a hit**. The source lies outside both. At
Samsung it is in the controller firmware area; at MediaTek presumably in the SoC/TEE, which
however is **not established**.

The two sources above point in the same direction: the Samsung key is a controller-side
secret, and the vendor route to it is a firmware read — not a user-area structure.

## extCSD of the cards we have (read, never written)

| Field | Value | Meaning |
|---|---|---|
| EXT_CSD_REV | 0x08 | eMMC 5.1 |
| SEC_COUNT | 30535680 | 15.63 GB = 0x3A3E00000 (covers the KD dump exactly) |
| BOOT_SIZE_MULT | 0x14 (20) | 2560 KiB = 2.5 MiB per boot partition |
| RPMB_SIZE_MULT | 0x1F (31) | 3968 KiB = 3.875 MiB RPMB |
| PART_SETTING_COMPLETED | 0x00 | partitioning **not** irreversibly locked |
| PARTITION_CONFIG | 0x48 | BootEnable = **BOOT2**, Access = BOOT1 |
| BOOT_BUS_WIDTH | 0x00 | 1 bit, no high-speed boot |
| BOOT_WP / WR_REL | 0x00 | no boot write-protect flags |

Affected: both Sony KD-49XD7005 cards and both Philips 65PUS810212 cards. They differ only
in `0xFE` (card firmware version) and `0x10C`/`0x10D` — the factory configuration is
identical across all of them.

**Consequence for the write plan:** the device boots from **BOOT2**. BOOT2 (2.5 MiB) must
therefore be written, or it will not start regardless of the RPMB state.
`PART_SETTING_COMPLETED` stays `0` — setting it to `1` would be **irreversible** and is not
needed according to the source cards.
