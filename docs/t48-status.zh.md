# T48 / eMMC —— 状态记录

除非明确标注为推测，以下所有内容均来自我们自己的 USB 抓包与卡片读取。
设备序列数据（原始 CID）已删除；卡型号与芯片版本保留，因为它们本身不具识别性。

| MID / PNM | 0x15（三星）/ **…JNB4R**，生产日期 2017-05 |

## 2. 卡片经历过什么

* `BOOT1.BIN` 与 `BOOT2.BIN`（各 4 MB）被回写，2 × 4 MB，无错误，随后做了 8 MB 回读校验。
* **用户区已备份且为空：** 通过我们自己的驱动完整读取 15 634 268 160 字节，
  ~11.8 MB/s。`find_metadata.py` 发现 **0 个被占用的 4-KiB 块**，无 CID / VCT0 / RPMB
  命中 —— 该芯片的整个用户区全为零。
* 对 RPMB 密钥的结论：**这颗芯片**上没有三星元数据块，因此用户区中没有密钥。
  元数据路径（另一张卡 KMDP6001DB-B425）在这里不适用。

### 2.1 插槽中的第二张卡（“JTD4R”）

* 容量与版本相同，`PARTITION_CONFIG` 0x00。
* 用户区**含有真实数据**：LBA 0 是 ARM 启动向量（`71 00 00 ea …`），分区从 0x40000
  开始，0x100000 处为 0xFF 填充，代码从 0x800000 开始。镜像中出现 MediaTek DRM 字符串
  如 `MTDRM_RPMBLoadMacKey`。
* 元数据搜索**为阴性**：任何字节序下都没有 CID，也没有“Boot Identification”。
  `VCT0` 与 `RPMB` 的命中位于用户数据中（Base64 字符串、MTK DRM 库）。
* **无 MBR / GPT / PGPT：** LBA 0 本身就是引导加载程序（`MTK/DTV/ROMCODE/MSDCBOOT`）。
  布局来自加载器，而不是分区表。
* 平台：MediaTek DTV，字符串“Preloader T8032”、“PH7M_EU_5596”，构建日期 2021-11-08。
* MTK DRM 库**通过 RPMB** 加载密钥（`MTDRM_RPMBLoadMacKey`），密钥并未保存在镜像中。
  因此设备镜像同样无法提供密钥。

## 3. T48 USB 协议（来自抓包）

帧：命令 `OUT 0x01` → 应答 `IN 0x81`；数据 `OUT 0x02` / `IN 0x82`。

**初始化：** `00`（信息，×2）· `24 f0` / `24 e0` / `24 f1`（会话）· `3e 01` · `03`（64 B，
BEGIN_TRANS）· `39`（状态）· `21`（能力）· `05` CID · `06` CSD · `08 48 00 02` extCSD ·
`04` END_TRANS。

**extCSD 应答：** 528 字节 = 8 字节头 + 512 字节 extCSD + 8 字节状态；
`extCSD[i] = buf[i+8]`，已用 EXT_CSD[162]=01、[179]=0x48、[192]=8、[212..215]=0x01D1F000
核对。

**单块读取**（依据抓包验证）：

```
27 46 00 00 00 03 b3 01             管道设置
14 00 00 00 00 00 00 00 01 00 00 02 寻址（块数 1）
OUT 512 B 至管道 0x02               控制缓冲：全零，token 位于 484–499，
                                    字节 511 = 0x02
15 00 00 02 00 00 00 00 01 00 00 02 读取
IN 0x82（最多 520）→ 528 字节        16 字节头 + 512 字节帧
```

**令牌链：** 主机每个会话生成 16 个随机字节，并且在其后的每个请求中都必须回显编程器
最后返回的那 16 字节。没有这个回显，编程器固件会等待并挂起；只有物理重插才能恢复。

**批量流：** 40 字节描述符，操作码 **`0d` = 读**，**`1f` = 写**：

| 偏移 | 值 | 含义 |
|---|---|---|
| +0 | 0x0d | 操作码，读 |
| +1 | 1 | 块模式（LBA 以 512 字节块计） |
| +4 | LBA | **起始地址**（`(byte_addr>>9) \| (high<<23)`） |
| +8 | 512 | 块大小 |
| +12 | 32 | 每 16-KiB 帧的块数 |
| +16 | 帧数 | 流中 16400 字节帧的数量 |
| +20 | 32 | 每帧地址步进 |
| +24 | 32 | 每帧块数 |
| +28 | 1 / 4 | 读 / 写 |
| +32 | 1 | 常量，来自 eMMC 初始化路径 |

- 转储从 **管道 0x82** 读取 **16400 字节**。管道 0x81 上 0x10040 的变体是空白检查路径，
  不是转储。
- 只有满足 `frame[0] & 0x7FFFFFFF == 0` 的帧才会被接受；否则厂商工具以
  “Error code / Status reg”中止。
- 我们早期自建的描述符总是把 +4 置为 0。驱动中已修正
  （`mass_descriptor(start_lba, frames)`）。

**写入路径**（从厂商二进制重建，已在设备上验证）：

- 描述符 `1f 01 …`，+28 = 4，其余字段与读相同。
- 16400 字节帧：头字节 0，+4 为递增 LBA（步进 32 块），+8 = 512，+12 = 32，
  从 +16 起为 16 KiB 数据。
- 每写满一个 1-MB 块后，**下一组的第一个帧**（第 64、128… 帧）头字节为 **2**；
  该帧之后主机从 `0x81` 读取 64 字节，并把字节 0 当作错误码。
- 结束：发送 STATUS `0x39`，从 `0x81` 读取 32 字节。字节 0 = 0x02 表示
  “EMMC Running TimeOut”；否则由 u16@+2 / u32@+4 组成错误文本。
- 中止/失败：发送头字节为 **1** 的帧，然后同样的结束流程。

**擦除（操作码 0x0e）：** 16 字节命令，字节 0 = `0e`，字节 4–7 = 起始 LBA，
字节 8–11 = **闭区间**结束 LBA。应答：从 `0x81` 读 8 字节，字节 1 = 错误码。每个块之前，
工具通过 CMD13（`0x4c`）检查卡状态，并轮询直到该区域不再忙碌。

写入与擦除已在设备上验证（BOOT1，空白）：

| 测试 | 结果 |
|---|---|
| 写 1 MB（64 帧） | 回读 1 048 576 字节，**0 处差异** |
| 写 4 MB（256 帧，3 次 1-MB 确认） | 4 194 304 字节，**0 处差异**，第 64 帧正确 |
| 擦除 2048 块（1 MB） | 回读探测：0 个非零字节 |
| 擦除 8192 块（4 MB） | 回读探测：0 个非零字节 |

仍由 `T48_ALLOW_WRITE=1` 锁定，避免任何脚本误写。

### 3.2 区域选择

区域选择通过 EXT_CSD[179] 中的 PARTITION_ACCESS 位：
`27 46 00 00 00 <value> <index> <access>`，access 1 = 置位，2 = 清除，3 = 写字节。

| 区域 | 命令序列 |
|---|---|
| USER | `27 46 00 00 00 07 b3 02`（清除第 0..2 位） |
| BOOT1 | `… 07 b3 02`，再 `27 46 00 00 00 01 b3 01` |
| BOOT2 | `… 07 b3 02`，再 `27 46 00 00 00 02 b3 01` |
| RPMB | `… 07 b3 02`，再 `27 46 00 00 00 03 b3 01` |

**修正：** 早期驱动版本只置位而不先清除。当启动分区处于活动状态时，访问位保持不变
—— 一次“USER”读取实际上可能在读 BOOT1。`setup_area()` 现在会先清除。

### 3.3 RPMB 区域返回错误帧

区域 3 读取的每个 512 字节块都在偏移 508 处以 `00 01 00 00` 结束。那是 RPMB 结果字段
**0x0001 = General Failure**：未认证时，卡在每个 16-KiB 块中返回相同的错误帧，
所以所有区域 3 的转储看起来都一样。这不是寻址错误。

在厂商工具内部的交叉核对：两条 RPMB 读取路径构造相同的请求 —— 类型 4（认证读取）、
设置了 nonce，但 **MAC 字节为零**。也就是说该工具是未认证读取 RPMB；在有密钥的卡上
必然得到 0x0001。唯一使用密钥的路径是“编程密钥”路径（类型 1）—— 它**设置**密钥，
不读取密钥。该软件中不存在读取密钥的路径。

### 3.4 驱动中的 RPMB 帧层（已在设备上验证）

14/15 路径的 528 字节应答是 **16 字节头 + 512 字节 RPMB 帧**。我们早前的笔记
“500 字节数据 + 16 字节令牌”是错的：在字节 500 处观察到的“令牌回显”就是 JEDEC nonce 字段。

| 偏移 | 字段 | 长度 |
|---|---|---|
| 0–195 | 填充（全零） | 196 |
| 196–227 | MAC | 32 |
| 228–483 | 数据 | 256 |
| 484–499 | nonce（被返回） | 16 |
| 500–503 | 写入计数器（仅应答） | 4 |
| 504–505 | 地址 | 2 |
| 506–507 | 块数 | 2 |
| 508–509 | 结果 | 2 |
| 510–511 | 请求/应答类型 | 2 |

大端 —— **但在 T48 上测得一个例外**：类型字段返回时字节顺序颠倒（类型 2 → `02 00`），
所以 `rpmb_parse()` 同时给出 `type` 与 `type_be`。

实测：

| 请求 | 结果 |
|---|---|
| 类型 2 计数器 | 结果 0x0000，计数器 **33 638**（0x00008366），nonce 正确返回 |
| 类型 4 读取，地址 0，MAC = 0 | 结果 **0x0001**，帧其余部分为空，nonce **未**返回 |
| 头字段 | 16 字节头的字节 5 = 0x09；含义仍不清楚 |

CLI：`t48_mmc.py rpmb counter` · `rpmb read <addr> [blocks]` · `rpmb result`。
由于“每会话一次读取”的规则：**每次进程运行只能发一个 RPMB 请求**。类型 3 的写入路径
有意未实现 —— 它需要我们没有的密钥。

## 4. 固件更新（FFU）—— 对 T48 已排除

* 厂商软件中**没有**关于 FFU、`EFAC60FC`/`CBAD1160`、CMD60/CMD62 或厂商命令的任何字符串。
  “Reflash firmware”只涉及编程器自身固件。
* `cmp r12b, 8` 路径与 CMD60 解锁码只存在于 UFPI 加密狗代码中。
* **T48 无法更新 eMMC 固件。** 存在匹配的镜像，但无法通过这个编程器载入。

### 4.1 FFU 参考流程（来自 EasyJTAG/UFPI，供以后的厂商工具使用）

前提：`EXT_CSD_REV`（字节 192）= 8，以及**同类卡片的控制器固件镜像**（不是设备 ROM）。

1. **解锁：** CMD60 `0xEFAC60FC`，然后 CMD60 `0xCBAD1160`。
2. **可选擦除：** CMD35 参数 0 → CMD36 参数 0 → CMD38，超时 120 s。
3. **写入：** CMD23 设为扇区数 → CMD25 覆盖整个区间；然后等待。
4. **校验：** CMD23 → CMD18 全部回读，逐块 `memcmp`。
5. **复位：** CMD0 使用保存的参数，等待 15 s，然后以 1 bit 重新初始化。

**风险 —— 任何尝试前必读：**

* 第 2 步以**组索引 0**擦除。若第 1 步解锁未生效，擦除会落到**用户区** ——
  这是整个项目中最危险的操作。只能在有完整备份且使用一张可弃置的卡时进行。
* FFU 需要**同类卡片**的控制器固件，而不是 Android/Tizen ROM。对于我们的 16 GB 卡，
  可用数据库中**没有精确匹配**，只有 32 GB 变体。不要未经测试就使用。

**与 RPMB 密钥的关系：** FFU 写入控制器固件；它**不读取密钥**。“编程新密钥”只在
RPMB **尚未编程**（计数器 0）时可行。我们的卡片计数器为 33 638，即 RPMB 已编程；
上面无法自由选择新密钥，而“Reset RPMB”会破坏 RPMB 内容。FFU 是否会自行重置 RPMB
状态**尚无依据** —— 不要依赖它。

## 4a. 算法文件（`.alg`）—— 容器已解析

现有 354 个文件，系列 `EMMC_41_18` … `EMMC_54_33`、`NAND_xx`、`SPI25Fxx`、
`28F32Pxx`、`TTL1` 等。**此处不发布任何 `.alg` 文件。**

| 偏移 | 内容 |
|---|---|
| 0x000 | 32 字节 ASCII 名称（“EMMC211210”、“EMMC”…） |
| 0x020 | 256 字节描述（现有文件均为空） |
| 0x120 | 4 个 DWORD 头值（此处均为 0） |
| 0x130–0x21F | 零填充 |
| 0x220 | DWORD **0x0005327C**，全部 354 个文件相同 |
| 0x224 | DWORD **校验和**，小端 |
| 0x228 | 16 字节 `FF` |
| 0x238 | 魔数 `99 55 66 AA`，其后为载荷 |

**校验和（已解出，354/354 文件吻合）：** 反射 CRC-32，多项式 `0xEDB88320`，
初值 `0xFFFFFFFF`，**无最终异或**（“JAMCRC”），覆盖 **0x228 至文件尾**的全部字节。
Python：`(zlib.crc32(d[0x228:]) ^ 0xFFFFFFFF) & 0xFFFFFFFF`。

**载入与上传：** 加载器接受的载荷上限为 **98 336 字节**，从 0x220 读入静态缓冲区，
然后向 **EP 0x01 OUT** 发送 8 字节 `{0x26, 0x00, 0x00, 0x00, <长度>}`，等待 100 ms，
再发送 0x220 起的缓冲区。也就是说，`.alg` 被**原样传给编程器并在那里执行**。
文件名由系列前缀（`EMMC_`、`NAND_`、`VGA_`…）+ 十六进制芯片索引 + eMMC 的 `_33`/`_18` 组成。

**载荷：** 16 位字流，小端，约 22 % 为零字；前 32 字节在**所有**系列中相同（共享前言）。
我们搜索了全部 354 个文件中的 FFU 常量字节模式：**0 命中**。eMMC 的 `.alg` 是编程器代码，
不是 MMC 命令流。

**我们的驱动不需要它：** 读/写/擦除走内置固件描述符（`0d`/`1f`/`0e`）。厂商工具额外
加载 `.alg`，是因为编程器从其中执行芯片专用流程。

## 5. 下一步

已在设备上完成：地址字段验证；完整用户区备份（全零）；`PARTITION_CONFIG` 复位；
写入与擦除逐字节一致；第二张卡已备份并离线分析；RPMB 帧层已构建并测量；
`.alg` 容器已解析。

驱动测试系列：`py_compile` 通过，`selftest` 25 项检查 / 0 错误；`read` 1 帧；
`dump --resume` 只补齐缺失帧；`verify` 报告 0 个差异块，翻转一个字节时返回 rc 5
并给出精确位置；无 `T48_ALLOW_WRITE=1` 时写/擦被拒绝；参数错误返回 rc 2。

**未决：**

1. **RPMB 密钥：** 在这颗芯片上无法通过用户区获得。只剩厂商侧 —— 带三星启动技巧的
   EasyJTAG 盒子，或 UFPI（`0x93`），两者都需要 Windows 和我们没有的硬件。
   T48 已被证实无法读取它。
2. **FFU：** 参考流程已记录（§4.1）。执行需要 EasyJTAG/UFPI 与匹配的控制器固件镜像；
   我们的 16 GB 卡没有精确匹配。
3. **转发：** T48 位流是否真的把 CMD60/CMD62 传给卡片，仍未证实 ——
   见 `../WEITERE-WEGE.md` 与 issue #1。
